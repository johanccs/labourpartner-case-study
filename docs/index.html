Case study

LabourPartner

A labour-relations compliance platform that guides South African employers through discipline, grievance and dismissal procedures — producing documentation that holds up when it is challenged.

01

The problem

South African employers must follow strict procedure to discipline or dismiss anyone. Under the Labour Relations Act (LRA), a dismissal is fair only if both the reason and the process were fair — the right charge sheet, the right notice periods, a properly constituted hearing, records kept as events happened rather than reconstructed afterwards.

One wrong step or one wrong clause turns a justified dismissal into a costly award at the Commission for Conciliation, Mediation and Arbitration (CCMA). The expertise needed to avoid that sits with labour consultants who bill by the hour. Smaller employers cannot retain one, so they improvise with borrowed templates and hope.

02

What it does

The system models the employment lifecycle as guided procedures, not as a document library. The document is an output of having completed the process. That inversion is the point: a template pack gives you paperwork, whereas a procedure gives you a record of having done the thing the paperwork claims.

  • Onboarding and contractsEmployment contracts, addendums, procedure manuals — assembled per employee from a versioned clause library.
  • DisciplineDisciplinary code, procedure, forms and warnings kept as separate concerns, so the code an employer adopted and the warning they issued are independently auditable.
  • Grievances and hearingsGrievance intake through to a properly constituted hearing, with the record built as the process runs.
  • Terminations and retrenchmentsDismissal and operational-requirement processes, including the consultation steps that make a retrenchment defensible.
  • StrikesProtected and unprotected industrial action, and the notices each requires.
  • AdministrationCompany and user setup, licensing, cart and payments, audit logging.
Known limitation

Clause overrides are currently stored globally, not per tenant: ClauseTexts is keyed on component and paragraph only, with no company column. An edit therefore applies across tenants. Tenant-scoped clause overrides are identified future work, and are the next structural change I would make.

03

Architecture

An Angular single-page client against an ASP.NET Core API over SQL Server, split into five projects plus tests. Dependencies point inward: the API layer knows about services, services know about the domain, and nothing in the domain reaches back out.

Authentication is JWT bearer with multi-factor verification and account lockout. Authorization runs on three tiers — User, CompanyAdmin, PlatformAdmin — but the tier alone does not grant cross-company access. Vendor-side reach is governed separately by group and capability membership, so a platform administrator's blast radius is something you configure rather than something they inherit.

04

Decisions

Five choices where the constraint mattered more than the technology, each with what it cost.

4.1

Three tiers, then capabilities on top

Role checks alone stopped working once vendor staff and tenant staff needed to see materially different systems rather than more or less of the same one. A tenant administrator manages one company; a platform administrator operates across companies, but only for the capabilities their group grants.

Trade-off  Two overlapping mechanisms to reason about. AdminType and CompanyAdmin also deliberately share the value 1, so existing call sites kept compiling — correct for migration, confusing on first read, and commented as such at the definition.

4.2

Migrating password hashes without locking anyone out

Passwords moved from unsalted SHA-256 to PBKDF2-SHA256 at 100,000 iterations with a 16-byte salt, stored as pbkdf2$<iterations>$<salt>$<hash>. Legacy hashes still verify on the old path, so the migration is invisible to users rather than a forced reset.

The interesting part was the failure. The password column was 80 characters, which fits a hex SHA-256 digest exactly and truncates a PBKDF2 string silently. The in-memory test database had no length constraint, so the suite stayed green while SQL Server quietly corrupted every new hash. It is now 255, and the reason is written in a comment above the field.

Trade-off  The legacy verification path has to live on until the last old hash is replaced, and there is no clean signal for when that is.

4.3

Clause history as a first-class output

Every clause edit archives the prior text to ClauseTextVersions with author and timestamp, and any archived version can be restored in place. For a compliance product this is not a convenience feature: the question at arbitration is what the wording said on the day it was issued, and that answer has to be recoverable.

Trade-off  Versions accumulate without a retention policy. More significantly, the clause tables carry no company column, so overrides are global rather than tenant-scoped — noted above as the next structural change.

LP.Persistence/Entities/ClauseText.cs · ClauseTextVersion.cs
4.4

Tenant isolation checked at the boundary

A valid token proves who you are, not what you may touch. Cart and payment operations compare the caller's company against the record's before acting, and refuse rather than filter: if (!User.IsPlatformAdmin() && User.GetCompanyId() != companyId) return Forbid();

These checks were added after an audit found endpoints that authenticated the caller and then trusted an identifier from the request body. Authenticated is not authorized, and an ownership check is the cheapest place to prove it.

Trade-off  Enforced per controller rather than centrally, so it holds only as long as every new endpoint remembers. A filter or policy would be structurally safer.

4.5

An AI feature is an operational liability first

A language model checks edited clause wording before it is issued and flags text that weakens the employer's position. Useful — and, shipped carelessly, an open invoice. The verification endpoint requires authentication and caps input at 8,000 characters, both added before a production API key existed rather than after a bill arrived.

Trade-off  A third-party model in the path of a compliance feature is a dependency on someone else's uptime, pricing and behaviour. It advises; it does not approve. The employer remains the decision-maker, which is the only defensible position for automated legal advice.

05

Deployment

Two repositories, two pipelines, one production environment. The API deploys to Azure App Service and the client to Azure Static Web Apps, each from its own GitHub Actions workflow on merge to main. Database migrations are a separate, deliberately narrower workflow.

Green does not mean live

The workflow reports success when the build is handed over to Azure, not when the new code starts answering requests. App Service still has to start the new process and warm it, which takes one to three minutes. During that window the old build is serving and the pipeline is green.

Verification order

Because the two repositories deploy independently, order matters. The client calls the API, so the API goes first and is confirmed answering before the client that depends on it ships. Only then are the security assertions checked against the live application.

Where this is weakest

Database migrations run from a separate workflow that is not gated on the test suite, and data migrations keyed on business values fail open rather than loudly. Affected rows have to be checked by hand before and after. This is the part of the pipeline I trust least and the next thing I would harden.

06

Rigour

Compliance software fails quietly. A wrong clause does not throw an exception — it sits in a contract until someone contests it, so the work has to be verified rather than assumed.

Backend tests229 passing, 0 failing. Controllers, services, processing and infrastructure, including authorization tests written to fail against the pre-fix code.
DeploymentGitHub Actions to Azure App Service for the API and Azure Static Web Apps for the client, with separate workflows for infrastructure and database migrations.
SecurityAn audit before launch found ten endpoints reachable unauthenticated, missing tenant ownership checks, and an unauthenticated AI endpoint. All closed and verified returning 401 in production.
Verified, not assumedEvery claim on this page was checked against the source or the database while writing it. The clause-scoping limitation above was found that way, and stated rather than dropped.
Operational note

A green pipeline is not a live deployment. App Service takes one to three minutes to complete a slot swap, which is long enough to mistake a successful deploy for a failed one and roll back something that was working.
